한국어 산문을 작성하기 전에 적용할 문체 규약을 확인하세요.

1. 현재 작업 디렉터리에 `docs/korean-style.md`가 있으면 해당 규약을 우선 적용하세요.
2. 저장소 규약이 없으면 [기본 문체 규약](references/style.md)을 적용하세요.
3. 한 문서 안에서 해요체와 습니다체를 섞지 마세요.

## Gemini로 초고 받기

번역투를 교정하거나 긴 산문을 작성할 때는 이 스킬 폴더의 `scripts/prose.ts`를 실행하세요.
스크립트 경로는 이 `SKILL.md`의 위치를 기준으로 정하고, 현재 작업 디렉터리는 대상 저장소로
지정하세요.

```bash
node <skill-directory>/scripts/prose.ts --medium 'GitHub PR 본문' "이 변경의 PR 본문"
git diff --stat | node <skill-directory>/scripts/prose.ts --medium 'GitHub PR 본문' "이 변경의 PR 본문"
```

- 인자에는 작성 요청을, 표준 입력에는 참고 자료를 전달하세요.
- `--medium` 옵션에는 `GitHub PR 본문`, `앱 내 안내 팝업`, `버튼 이름`, `SNS 스레드`,
  `내부 개발 문서`처럼 실제 출력 매체를 지정하세요.
- `OPENROUTER_API_KEY` 환경변수가 없으면 작업을 멈추고 설정 방법을 안내하세요.
- 짧은 한 줄 주석이나 변수명처럼 도구를 실행하는 비용이 더 큰 작업은 직접 처리하세요.

## 결과 검증

출력 결과는 초고로만 활용하세요. 모델이 저장소의 파일 경로, 줄 수, 동작을 지어낼 수 있으므로
원본 자료와 대조하여 사실관계를 확인하세요. 숫자와 고유명사도 함께 검증하세요.

- 입력과 참고 자료로 뒷받침되지 않은 주장, 수치, 출처를 추가하지 않았는지 확인하세요.
- 과장된 의미 부여, 홍보성 수식어, 출처가 모호한 표현이 남아 있지 않은지 확인하세요.
- 내용 없는 꼬리 문장이나 요청하지 않은 전망, 도전 과제, 결론을 덧붙이지 않았는지 확인하세요.
- 상투적인 병렬 구조, 기계적인 세 항목 나열, 과도한 볼드체와 기호가 없는지 확인하세요.
- UI 문구는 사실 중심 원칙을 지키면서도 사용자에게 필요한 친절함을 유지하세요.

em-dash나 en-dash가 포함되어 있으면 그대로 출력하지 마세요. 공백 하이픈, 쉼표, 콜론으로
고친 뒤 다시 검증하세요.
